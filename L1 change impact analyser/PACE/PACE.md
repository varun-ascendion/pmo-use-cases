# BRD: Payments Middleware Platform – Reject Unstructured Beneficiary Addresses; Enforce Structured/Hybrid Address Formats (ISO 20022 CBPR+ / HVPS+)

| Field | Value |
|---|---|
| BRD Reference | BRD-PAYMENTS-2026-001 |
| Regulation | ISO 20022 Payments Migration – Structured Address Mandate (SWIFT CBPR+ usage guidelines; ECB T2/TARGET HVPS+ guidelines; Federal Reserve / EPC SCT Inst rulebooks aligned to ISO 20022) |
| Change Type | Rule-engine update + Schema validation + Message transformation update |
| Status | Draft v0.1 |
| Date | 23 June 2026 |

## 1. Purpose
This BRD defines the changes required to the Payments Middleware Platform to reject inbound and outbound ISO 20022 payment messages that carry the beneficiary (Creditor) postal address in unstructured form, and to accept only fully Structured or Hybrid address formats in line with the global ISO 20022 community mandate. Out-of-scope items include changes to the Debtor (originator) address format handling beyond what is required for symmetric validation, and any changes to legacy MT message flows.

## 2. Regulatory Driver
- **Governing bodies / rulebooks:** SWIFT CBPR+ Usage Guidelines for cross-border payments; Eurosystem T2 / TARGET HVPS+ Usage Guidelines; EPC SCT/SCT Inst Rulebooks; Federal Reserve FedNow / Fedwire ISO 20022 specifications.
- **Requirement:** From the industry-coordinated cut-over date, the `<PstlAdr>` element within `CdtrAgt`, `Cdtr`, `DbtrAgt`, `Dbtr` and related parties in pacs.008, pacs.009, pain.001 and camt.05x messages must use **Structured** sub-elements (e.g., `StrtNm`, `BldgNb`, `PstCd`, `TwnNm`, `Ctry`) or **Hybrid** (a defined subset of structured elements alongside up to two `AdrLine` occurrences). Fully unstructured `AdrLine`-only addresses must be rejected.
- **Effective date:** 22 November 2026 (industry coordinated global activation date — *to be confirmed* against final SWIFT / Eurosystem release notes).
- **Gap:** The Payments Middleware currently accepts and forwards ISO 20022 messages containing unstructured `AdrLine`-only beneficiary addresses without validation against the Structured/Hybrid rule. There is no schema-level or rule-engine enforcement of the address format. Consequence of inaction: outbound messages will be rejected by SWIFT/market infrastructures from the effective date, leading to payment failures, NACKs, SLA breaches, customer impact and regulatory non-compliance.

## 3. Functional Requirements

| ID | Requirement | Source |
|---|---|---|
| FR-01 | The platform shall validate the `<CdtrPstlAdr>` element on every inbound pacs.008, pacs.009 and pain.001 message to determine whether the address is Structured, Hybrid or Unstructured. | CBPR+ Usage Guidelines – Postal Address Rules |
| FR-02 | The platform shall reject any inbound payment message in which the beneficiary postal address is fully unstructured (i.e., contains only `AdrLine` elements with no Structured sub-elements). | CBPR+ Usage Guidelines; HVPS+ Address Rules |
| FR-03 | The platform shall accept beneficiary addresses provided in Structured format where `TwnNm` and `Ctry` are present as a minimum. | CBPR+ Usage Guidelines – Mandatory Structured Elements |
| FR-04 | The platform shall accept beneficiary addresses provided in Hybrid format where `Ctry` and at most two `AdrLine` occurrences are present alongside permitted Structured elements. | CBPR+ Usage Guidelines – Hybrid Option |
| FR-05 | The platform shall return a structured rejection response (pacs.002 with reason code `BE16` or equivalent `AC01`/`AC03` per scheme) when a message is rejected for unstructured beneficiary address. | ISO 20022 External Code Sets; CBPR+ Reason Codes |
| FR-06 | The platform shall log every rejection with message identifier, party identifier, rejection reason and timestamp for audit and operational dashboards. | Internal Audit Policy aligned to CBPR+ traceability |
| FR-07 | The platform shall enforce the same Structured/Hybrid validation on outbound messages generated by the platform before dispatch to SWIFT / RTGS / Instant rails. | CBPR+ / HVPS+ Outbound Conformance |
| FR-08 | The platform shall expose configuration to enable or disable the rejection rule per channel (cross-border vs domestic) to support phased adoption. | HVPS+ vs CBPR+ scheme-specific activation timelines |
| FR-09 | The platform shall surface validation results to the operations console with filterable views by reason code and corridor. | Operational Readiness – CBPR+ Go-Live |

### 5.2 Rule Engine Logic

**Rule ID: RULE-ADDR-001 – Beneficiary Address Format Validation**

Current:
```
IF message.type IN (pacs.008, pacs.009, pain.001) THEN
    IF Cdtr.PstlAdr IS PRESENT THEN
        ACCEPT message
    END IF
END IF
```

Target:
```
IF message.type IN (pacs.008, pacs.009, pain.001) THEN
    addr := Cdtr.PstlAdr
    hasStructured := ANY(addr.StrtNm, addr.BldgNb, addr.PstCd, addr.TwnNm, addr.CtrySubDvsn) IS PRESENT
    adrLineCount := COUNT(addr.AdrLine)
    countryPresent := addr.Ctry IS PRESENT

    IF hasStructured AND adrLineCount = 0 AND addr.TwnNm IS PRESENT AND countryPresent THEN
        addr.format := STRUCTURED
        ACCEPT message
    ELSE IF hasStructured AND adrLineCount BETWEEN 1 AND 2 AND countryPresent THEN
        addr.format := HYBRID
        ACCEPT message
    ELSE
        addr.format := UNSTRUCTURED
        REJECT message WITH reasonCode = "BE16"
    END IF
END IF
```

**Rule ID: RULE-ADDR-002 – Outbound Address Conformance**

Current:
```
ON outbound_construction:
    COPY internal.address.lines -> PstlAdr.AdrLine[]
    EMIT message
```

Target:
```
ON outbound_construction:
    IF internal.address.format = STRUCTURED THEN
        MAP internal -> PstlAdr.StrtNm, BldgNb, PstCd, TwnNm, CtrySubDvsn, Ctry
    ELSE IF internal.address.format = HYBRID THEN
        MAP internal -> PstlAdr.Ctry, AdrLine[1..2] AND any available Structured sub-elements
    ELSE
        HALT construction
        RAISE outboundConformanceError
    END IF
    EMIT message
```

### 5.3 New Validation Rules

| Rule ID | Field | Rule | Error Behaviour |
|---|---|---|---|
| VAL-01 | Cdtr.PstlAdr | At least one Structured sub-element must be present, OR Hybrid combination valid | Reject with pacs.002 reason `BE16` |
| VAL-02 | Cdtr.PstlAdr.Ctry | Must be a valid ISO 3166-1 alpha-2 country code | Reject with reason `AC01` |
| VAL-03 | Cdtr.PstlAdr.AdrLine | Maximum 2 occurrences when format is Hybrid; 0 when Structured | Reject with reason `BE16` |
| VAL-04 | Cdtr.PstlAdr.TwnNm | Mandatory when format = Structured | Reject with reason `BE16` |
| VAL-05 | Cdtr.PstlAdr | Total content of `AdrLine` must not exceed 70 characters per line | Reject with reason `BE16` |

## 6. Out of Scope
- Changes to Debtor party address validation beyond schema alignment — *reason: regulatory mandate focuses on beneficiary (Creditor) addresses; Debtor-side validation will be addressed in a separate phase.*
- Legacy MT103/MT202 message validation — *reason: the mandate applies to ISO 20022 messages; MT decommissioning is governed by a separate SWIFT MT/MX co-existence programme.*
- Customer onboarding/CRM data quality remediation — *reason: data sourcing and customer record cleansing are owned by the originating channels and customer master data programme.*
- Back-population of historical payment records with Structured address fields — *reason: only forward-flow messages are within the regulatory scope.*
- Changes to sanctions screening logic on address fields — *reason: screening engine is a separate platform with its own change governance.*

## 7. Assumptions & Constraints

| Ref | Assumption | Risk if Invalidated |
|---|---|---|
| A1 | The industry effective date is 22 November 2026 (*to be confirmed* against final SWIFT/ECB release notes). | If the date shifts earlier, delivery window compresses and may miss go-live; if later, parallel-run effort extends. |
| A2 | Upstream originating channels (e.g., corporate channels, retail banking, file ingestion) will supply Structured address sub-fields ahead of platform go-live. | If upstream data is not Structured, the platform will reject genuine customer payments at high volume, causing customer impact and operational backlog. |
| A3 | The ISO 20022 External Reason Code `BE16` (or scheme-specific equivalent) is the agreed rejection code for unstructured beneficiary address. *Unconfirmed rule ID — to be validated with Scheme/Regulatory SME.* | If a different code is mandated, downstream consumers and reporting will misclassify rejections and require rework. |
| A4 | Reference data for ISO 3166-1 country codes is sourced from the existing reference data provider and will remain current. *Vendor sourcing dependency.* | If reference data is stale or unavailable, valid addresses may be rejected, causing false positives. |
| A5 | No back-population of historical records is required; the change applies only to messages processed after go-live. | If regulator requires retroactive remediation, a separate data migration workstream will be needed. |
| A6 | Schema artefacts (XSDs) for CBPR+ and HVPS+ usage guidelines will be made available by SWIFT/ECB at least 8 weeks before go-live. | If schemas arrive late, integration testing window is compressed and delivery risk increases. |

## 8. Acceptance Criteria
- Inbound pacs.008/pacs.009/pain.001 messages with fully unstructured beneficiary addresses are rejected with the agreed reason code in 100% of test cases.
- Inbound messages with Structured beneficiary addresses (TwnNm and Ctry minimum) are accepted and forwarded without alteration.
- Inbound messages with Hybrid beneficiary addresses (≤2 `AdrLine` with Ctry and at least one Structured sub-element) are accepted.
- Outbound messages constructed by the Transformation Service never contain fully unstructured `PstlAdr`.
- Persistence Store records include the Structured address sub-fields and the `AddressFormatType` classification for every processed message.
- Rejection events are logged with message ID, party ID, reason code and timestamp; visible in the Operations Console within 5 seconds of rejection.
- Configuration flag per channel (cross-border vs domestic) toggles enforcement without code change and is auditable.
- pacs.002 negative responses are schema-valid and contain the agreed reason code.
- End-to-end regression confirms no degradation in straight-through processing rate for compliant messages.
- Operational runbook updated; ops team trained on new rejection reason classification.

## Execution Summary
The BRD addresses the Payments Middleware Platform's adaptation to the ISO 20022 industry mandate that prohibits fully unstructured beneficiary postal addresses and requires Structured or Hybrid address formats. The change introduces new schema validation and rule-engine logic (RULE-ADDR-001, RULE-ADDR-002), five new validation rules (VAL-01–VAL-05), extensions to the Canonical Data Model and Persistence Store to carry Structured sub-fields, updates to the Transformation Service for outbound conformance, and new operational visibility for address-related rejections. Effective date is taken as 22 November 2026 subject to confirmation, with six assumptions flagged including upstream data readiness, reason-code confirmation and vendor reference data dependency.
